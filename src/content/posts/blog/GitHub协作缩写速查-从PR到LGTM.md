第一次给别人的开源项目提 PR，收到一条 `LGTM, thanks!`，人是懵的——是过了还是没过？`WIP: 先放一半` 又是在跟谁说？

这些缩写不是程序员自创的黑话，它们大多来自 Linux 内核邮件列表和早期的 Google/Mozilla 评审文化，现在已经是 GitHub、GitLab、Gerrit 甚至公司内部 IM 的通用语。本文按「提 PR → 求评审 → 被评审 → 收尾」的实际流程梳理一遍，最后给一份能直接抄的模板。

## 一、先看一张总表

| 缩写 | 全称 | 中文 | 谁在什么时候用 |
|---|---|---|---|
| PR | Pull Request | 合并请求 | 你要把自己的改动合进别人的仓库 |
| WIP | Work In Progress | 进行中，别合 | 提交时还没写完的作者 |
| PTAL | Please Take A Look | 请看下 | 作者请求评审 |
| TBR | To Be Reviewed | 待评审 | 请求（或提醒）有人来审 |
| LGTM | Looks Good To Me | 我觉得没问题 | 评审者通过 |
| SGTM | Sounds Good To Me | 同上，听着不错 | 评审者通过（多用于方案/设计讨论） |
| TL;DR | Too Long; Didn't Read | 太长了，懒得看 | 长文作者主动加摘要 |
| AFAIK | As Far As I Know | 据我所知 | 任何不确定的陈述前 |
| CC | Carbon Copy | 抄送 | 让某人也看到，但不要求他处理 |

下面逐个拆，重点不在翻译，在于**它在协作里承担什么作用**。

## 二、PR：Pull Request

字面是「拉取请求」，实际语义是「**请求你把我这个分支的改动合并进去**」。方向别搞反：是**你请求别人拉你**，不是你去拉别人。所以「我会提交一个 PR」= 我会开一个合并请求给你审。

一个 PR 打开时应该自带三件事：**改了什么、为什么改、怎么验证的**。缺了第三项的 PR，评审者只能靠读代码猜，效率很低。

## 三、WIP：Work In Progress

大改动写到一半，想先得到反馈，又怕维护者直接合了。WIP 就是那个「**安全阀**」。

用法有三种，力度不同：

1. **标题前缀**：`WIP: 重写解析器（第一步）`——最通用，一眼可见。
2. **Draft PR**：GitHub 官方形态，按钮一点就变成 Draft，且默认不能被合并，比手写 `WIP:` 更硬。
3. **正文里说明**：`还差错误处理，先放上来看看方向对不对`

重点：WIP 状态下，**要说清楚「哪些已完成、哪些还没」**。像 `WIP: 写了一半` 这种，维护者不知道从哪看起，等于没写。对维护者的价值在于——他能先审已经完成的部分，你少走回头路。

写完把标题里的 WIP 去掉，或点 `Ready for review`，这个动作本身就是一次「我准备好了」的信号。

## 四、PTAL：Please Take A Look

**请求项目维护人员进行 code review**。它是一句礼貌的「来人看看」，也是把「我已就绪」和「请审」合成一个动作。

典型位置：PR 描述末尾、或者评论里 `@maintainer PTAL`。

和 WIP 搭配很自然：

```text
WIP: 加个导出功能
目前已支持 Markdown，PDF 还没做。PTAL，先确认一下接口设计。
```

这里的 PTAL 只要方向确认，不要求逐行读。

补两个同族说法，Gerrit 用户天天见：`PTAL` 有时写作 `PTLG`（Please Take a Look, Gerrit 语境），意思一样，不必纠结。

## 五、TBR：To Be Reviewed

**提示这些代码需要被审核**。和 PTAL 的区别在语气和作用点：

- PTAL 是**对评审者说的**：请你来看。
- TBR 是**给改动贴标签**：这块**还没人审过**。

实际用起来，TBR 常见于两种场景：提交信息里 `TBR: 这部分涉及编解码，需要专人看`；或者小仓库里没什么人管 PR，作者在评论里 `TBR @someone` 催一下。

有个容易误解的点：在 Google 内部流程里 `TBR` 也有「**Trusted Bot Reviewer / 直接合入不经人审**」的写法，和「待评审」正好反过来。所以你看到 TBR 时，最好结合上下文判断是「请来审」还是「跳过审核」，别硬套。

## 六、TL;DR：Too Long; Didn't Read

直译「太长，没读」，但现在**基本只剩一个用法：作者给自己长的内容加一句摘要**。它不是骂人话，是排版工具。

```markdown
TL;DR：把构建脚本拆成三段，本地构建快了 40%，CI 配置需要同步改一处。
```

反过来，如果有人在你 PR 下面回 `TL;DR`，多半就是在说：描述太啰嗦了，**把结论写前面**。这是很友好的提醒，值得改。

> 老写法 `TL;DR`（带分号）和 `tl;dr` 都对，`TLDR` 也常见，别在标点较劲。

## 七、LGTM / SGTM：审核通过

**LGTM = Looks Good To Me = 我觉得这个可以**，是 code review 里出现频率最高的通过语。看到它基本等于过了（当然还有 `LGTM, but nits` 这种「过了，但有几处小问题」，见下文）。

**SGTM = Sounds Good To Me = 听起来不错**，和 LGTM 同义，但语感更偏**方案、设计、计划**，而不是具体代码行。讨论技术选型时回 `SGTM` 比 `LGTM` 自然。

另外几个常一起出现的「不完全通过」：

| 说法 | 意思 |
|---|---|
| `LGTM with nits` | 可以合，但有几处小问题（nit = 吹毛求疵级） |
| `LGTM once CI passes` | 等 CI 绿了就合 |
| `not LGTM` | 我不同意，别合（语气很重，慎用） |

想表达得更完整，一句话就够：`LGTM，nits 可以后续再修。`

## 八、AFAIK：据我所知

**AFAIK = As Far As I Know**。它的真正价值不是省字，而是**诚实地标记不确定性**。

对比一下：

- `这个配置项会覆盖默认值。` —— 说错了就是误导。
- `AFAIK，这个配置项会覆盖默认值。` —— 给了对方核实的余地。

评审里几乎一半的分歧来自「不确定但说得像确定」。加个 AFAIK/IIRC，成本为零，收益很高。同族还有 IIRC（If I Remember Correctly）、IMHO（In My Humble Opinion）。

## 九、CC：Carbon Copy

**CC = 抄送**，来自邮件时代的复写纸。语义很精确：**让某人也看到，但不要求他做事**。

GitHub 里没有真正的 CC 字段，做法是用 `@` 提及，但要在正文里**点名说明意图**，否则被 @ 的人以为在派活：

```text
CC @alice —— 这条改了公共接口，供你知会，不需要处理。
```

公司内部改用 IM/邮件时，CC 就按字面意思用：抄给相关人，责任人不变。

## 十、拼成一段对话

把上面的词放进真实场景，基本是这样流动的：

```text
作者：WIP: 支持导出 CSV（已支持 UTF-8，GBK 还没做）
作者：（第二天）做完了，去掉 WIP。PTAL @maintainer
      TL;DR：新增 1 个文件、改 2 处调用，导出复用现有序列化逻辑。
评审者：AFAIK，这里用 String() 会把 null 变成 "null"，确认下？
作者：确实是，改成 ?? ''，已 push。
评审者：LGTM，nits 可以后续再修。
维护者：SGTM，CC @release-manager，下个版本带这功能。
```

一句话都没用完整句子，但**谁该做什么清清楚楚**。这就是缩写的意义——不是炫技，是压缩协作的沟通成本。

## 十一、几个容易翻车的点

1. **`LGTM` 不是合并**。评审通过 ≠ 有权合并，合并动作一般是维护者做。
2. **`WIP` 别忘摘**。忘了摘的 PR 会一直卡在 Draft，维护者以为你还没弄完。
3. **别对小改动滥用缩写**。一句 `请帮忙看下这个修复` 比 `PTAL` 更不容易误解，尤其对刚接触开源的维护者。
4. **`TBR` 有双义**，如上所述，用在描述里时把话说完整：`TBR: 需要 code owner 过一遍`。
5. **缩写不能替代信息**。`LGTM` 后面跟一句「我重点看了错误处理」，比单发一个 LGTM 有用得多。

## 结语

记住九件事就够：**PR 是请人合你的代码；WIP 是别合；PTAL 是来看；TBR 是还没人看；TL;DR 是把结论放前面；LGTM / SGTM 是过了；AFAIK 是我也不确定；CC 是知会不派活。**

下次收到一句 `LGTM`，可以安心去等合并了。
